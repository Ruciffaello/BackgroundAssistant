# BackgroundAssistant 重要決策

本文件只記錄會長期影響架構、開發方向或後續判斷的重要決策。一般實作細節由程式碼與 Git 歷史保存。

## DEC-001 採用輕量文件管理

- 日期：2026-08-21。
- 決定：以 `PROJECT_STATUS.md` 作為總覽、`TASKS.md` 作為唯一工作狀態來源、`DECISIONS.md` 記錄重要決策，長篇分析才放入 `reports/`。
- 原因：保留必要的可追蹤性，同時降低工程師查找及維護文件的時間。
- 維護原則：同一資訊只記錄一次；只寫無法由程式碼、Git 或自動化工具直接回答的內容。
- 重新評估：團隊規模或交付流程變得無法由目前結構支援時。

## DEC-002 採用雙向 MCP 與 DLL 插件並存的產品定位

- 日期：2026-08-21。
- 決定：產品目標同時具備 MCP Client 與 MCP Server 能力，並可透過 DLL 插件提供本機功能；對外可依合作協議呼叫合作方或第三方 MCP Server 工具。
- 原因：產品需要統一運用內建能力、本機擴充及外部合作工具，而不是被限定為單一 Client 或 Server。
- 現況：目前只有程序內本地工具原型；標準 MCP 與 DLL 插件機制尚未實作，也尚未排入近期工作。
- 影響：未來需要統一工具目錄、來源 adapter、雙向協定邊界，以及獨立的對外授權政策。
- 重新評估：開始設計插件契約或確定第一個合作方 MCP Server 時，評估實作順序與最小範圍。
- 參考：[MCP 對接差異報告](reports/MCP_INTEGRATION_GAP.md)。

## DEC-003 先建立對話資料庫，不同時實作長期記憶

- 日期：2026-08-21，2026-08-24 修訂。
- 決定：SQLite 目前只實際承擔固定使用者與完整對話回合；`MemoryItems` 只建立資料表，尚未接上保存或搜尋。Profile、MemoryWorker 與安全確認流程暫不實作。
- 原因：先驗證對話延續與資料庫生命週期，避免把「記憶」一次擴大成抽取、分類、覆寫及向量平台。
- 範圍：四表為 `SchemaMigrations`、`Users`、`ConversationMessages`、`MemoryItems`；沒有 Profile 或 Session 資料表。
- 重新評估：對話上下文穩定後，再逐項決定長期記憶寫入、敏感資料與搜尋規則。
- 參考：[使用者記憶設計（精簡版 V1）](reports/USER_MEMORY_DESIGN.md)。

## DEC-004 對話為預設路徑，工具需求才攔截

- 日期：2026-08-24。
- 決定：Router 只輸出 `conversation` 或 `tool`，並附帶 `subject`；明確工具需求在同一次 LLM 推論中產生工具名稱與參數。
- 失敗策略：無效 JSON、未知模式或不可用工具一律回到一般對話，不再轉成 `clarify`。
- 原因：六 action 彼此重疊，且技術錯誤統一降級成 `clarify`，造成所有輸入看似語意不明。
- 影響：移除第二次 Tool Planner；模糊需求由對話模型自然追問。
- 重新評估：工具數量增加到單一 Prompt 無法穩定描述，或開始使用動態 Tool Registry 時。

## DEC-005 使用 BM25 篩選最近對話

- 日期：2026-08-24。
- 決定：目前輸入與最近兩輪的使用者原文使用中文字元 bigram BM25 比較，達門檻才把該輪完整內容加入回答 Prompt。
- 原因：避免無關舊對話污染回答，同時不引入 embedding 模型、自製 tokenizer、向量資料庫或額外 LLM Stage。
- 限制：BM25 比較詞彙而非完整語意，代名詞與同義詞可能漏判，通用詞可能誤判。
- 重新評估：實機案例顯示分詞、停用詞與門檻仍無法控制誤判時。

## DEC-006 採用按需延遲載入與影子副本之 DLL 工具插件機制

- 日期：2026-08-25。
- 決定：
  1. **啟動時輕量掃描**：Host 啟動時僅由 `ToolManifestCatalog` 讀取 `plugins/*/plugin.json`，不預載任何 Tool DLL。
  2. **按需載入 (On-Demand)**：Router 觸發工具執行時，由 `LazyDllToolLoader` 計算 DLL SHA-256 指紋並載入。
  3. **影子副本防鎖檔**：複製至 `.plugin-cache/` 並從記憶體資料流載入，避免 Windows 作業系統鎖定來源 DLL 檔案。
  4. **可回收 ALC 與損壞回退**：使用 collectible `AssemblyLoadContext` 隔離，當新版本 DLL 損壞或載入失敗時，保留並回退至上一版已載入實例，維持系統高可用。
- 原因：避免所有工具在 Host 啟動時佔用記憶體與啟動時間，並確保在開發或熱更新時不會因檔案被佔用而無法編譯或部署。
- 重新評估：若插件數量極大或需要動態熱卸載與複雜生命週期時。
