# BackgroundAssistant 重要決策

本文件只記錄會長期影響架構、開發方向或後續判斷的重要決策。一般實作細節由程式碼與 Git 歷史保存。

## DEC-001 採用輕量文件管理

- 日期：2026-08-21。
- 決定：以 `PROJECT_STATUS.md` 作為總覽、`TASKS.md` 作為唯一工作狀態來源、`DECISIONS.md` 記錄重要決策，長篇分析才放入 `reports/`。
- 原因：保留必要的可追蹤性，同時降低工程師查找及維護文件的時間。
- 維護原則：同一資訊只記錄一次；只寫無法由程式碼、Git 或自動化工具直接回答的內容。
- 重新評估：團隊規模或交付流程變得無法由目前結構支援時。

## DEC-002 採用雙向 MCP 與 DLL 插件並存的產品定位

- 日期：2026-08-21。
- 決定：產品目標同時具備 MCP Client 與 MCP Server 能力，並可透過 DLL 插件提供本機功能；對外可依合作協議呼叫合作方或第三方 MCP Server 工具。
- 原因：產品需要統一運用內建能力、本機擴充及外部合作工具，而不是被限定為單一 Client 或 Server。
- 現況：目前只有程序內本地工具原型；標準 MCP 與 DLL 插件機制尚未實作，也尚未排入近期工作。
- 影響：未來需要統一工具目錄、來源 adapter、雙向協定邊界，以及獨立的對外授權政策。
- 重新評估：開始設計插件契約或確定第一個合作方 MCP Server 時，評估實作順序與最小範圍。
- 參考：[MCP 對接差異報告](reports/MCP_INTEGRATION_GAP.md)。

## DEC-003 使用精簡的使用者記憶第一版

- 日期：2026-08-21。
- 決定：使用獨立 SQLite 儲存 Profile、最近對話與長期記憶；目前使用固定 `local-default`，回答完成後再以完整 `MemoryJob` 快照進行背景記憶分析。
- 原因：先滿足連續對話與安全保存需求，同時避免為尚未實作的聲紋、RAG、多使用者併發及歷史版本建立過多資料表與抽象層。
- 安全原則：明確更正才覆蓋、相容資料才合併、不確定不儲存；敏感資料需要確認，密碼、身分證號、驗證碼及金鑰等資料一律拒絕。
- 範圍：第一版不使用 `TurnId`，Profile 使用單一 `ProfileJson`，最近對話保存 30 天並在接近 token 上限時才摘要。
- 重新評估：聲紋辨識、RAG、跨重啟待確認項目或複雜 Profile 查詢出現實際需求時。
- 參考：[使用者記憶設計（精簡版 V1）](reports/USER_MEMORY_DESIGN.md)。
